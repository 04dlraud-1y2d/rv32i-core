# RV32I 싱글사이클 코어 — 일주일 독해 가이드

ALU는 이미 만들어 보셨으니, 나머지는 **배선과 제어**입니다.
이 저장소는 RV32I 기본 정수 명령 전체가 돌아가는 싱글사이클 코어 하나와,
그걸 검증하는 테스트벤치, 그리고 테스트 프로그램을 만들 어셈블러로 구성됩니다.

검증 상태: **40개 항목 전부 통과 / 58 사이클에 ecall 도달** (iverilog 12.0).

---

## 바로 돌려보기

```bash
make          # 어셈블 → 컴파일 → 실행 → PASS/FAIL 요약
make trace    # 매 사이클 PC와 명령어 출력
make wave     # wave.vcd 생성 → gtkwave로 파형 확인
```

`$readmemh ... Not enough words` 경고는 정상입니다.
명령어 메모리를 1024워드로 잡았는데 프로그램이 64워드라서 나는 것으로,
남은 공간은 NOP으로 초기화되어 있습니다.

---

## 파일 구조

- `rtl/rv32i_defs.vh` — opcode, 먹서 선택값 등 공통 상수 (ALU 코드는 `alu_defs.vh`에서 include)
- `rtl/alu32.v` — **본인이 만든 구조적 ALU** (CLA + 배럴시프터 + 플래그)
- `rtl/alu_defs.vh` — ALU 연산 인코딩 `{funct7[5], funct3}`
- `rtl/regfile.v` — 32×32 레지스터. **비동기 읽기 / 동기 쓰기**
- `rtl/imm_gen.v` — immediate 추출·부호확장 (I/S/B/U/J)
- `rtl/control.v` — 메인 디코더. opcode → 제어신호 진리표
- `rtl/branch_unit.v` — 분기 조건 판정 6종
- `rtl/lsu.v` — 바이트/하프워드 정렬 처리 (LB/LH/SB/SH)
- `rtl/instr_mem.v` — 명령어 ROM (비동기)
- `rtl/data_mem.v` — 데이터 RAM (비동기 읽기 / 동기 쓰기 + 바이트 마스크)
- `rtl/rv32i_top.v` — 데이터패스 배선 + PC 갱신 로직
- `test/tb_rv32i.v` — 테스트벤치 (레지스터·메모리 최종값 검사)
- `test/test_rv32i.s` — 전 명령어 테스트 프로그램
- `tools/asm.py` — 최소 RV32I 어셈블러 (라벨, 의사명령 지원)

## 7일 독해 순서

읽는 것만으로는 안 남습니다. 각 날짜마다 **"직접 할 일"** 을 꼭 하세요.
전부 1~2시간 안에 끝나는 분량입니다.

### 1일차 — 전체 그림과 ISA 포맷

읽기: `rv32i_defs.vh` → `test/test_rv32i.lst` (어셈블 결과 리스팅)

- RV32I 6개 포맷(R/I/S/B/U/J)이 각각 어떤 필드를 쓰는지 종이에 그리세요.
- 리스팅에서 `addi x1, x0, 10` → `00a00093` 이 어떻게 나왔는지 손으로 비트를 쪼개보세요.

직접 할 일: `make trace` 를 돌려서 PC가 4씩 증가하다가 분기에서 튀는 지점을 눈으로 확인.

### 2일차 — immediate 생성 (여기가 1차 관문)

읽기: `imm_gen.v`

- B타입과 J타입의 비트가 왜 그렇게 흩어져 있는지. 힌트: 포맷이 달라도 같은 비트 위치를 재사용해서 먹서를 줄이려고 일부러 그렇게 배치했습니다.
- 모든 포맷이 `instr[31]`을 부호비트로 쓰는 이유.
- B/J의 `imm[0]`이 명령어에 없고 상수 `1'b0`인 이유.

직접 할 일: `tools/asm.py` 의 `b_type()`, `j_type()` 함수와 `imm_gen.v` 를 나란히 놓고 비교하세요. 인코더와 디코더가 정확히 역함수입니다. 이걸 확인하면 이 부분은 끝납니다.

### 3일차 — 제어 유닛

읽기: `control.v`

- `case (opcode)` 의 각 항목을 데이터패스 그림의 먹서/인에이블과 1:1로 연결하세요.
- `decode_alu()` 의 비대칭에 주의: OP_IMM에는 SUBI가 **없지만** SRAI는 **있습니다**. 그래서 funct3=000은 즉치일 때 funct7을 무시하고, funct3=101은 봐야 합니다.
- LUI를 `0 + imm`으로, AUIPC를 `PC + imm`으로 처리한 이유 (ALU 재사용).

직접 할 일: `control.v`를 덮고, 명령 10개를 골라 제어신호 표를 직접 채운 뒤 코드와 대조하세요.

### 4일차 — 데이터패스 배선

읽기: `rv32i_top.v`

- 섹션 7~11만 집중하세요. 특히 `pc_next` 우선순위:
  `jalr > (jal 또는 분기성립) > pc+4`
- JALR이 `{alu_y[31:1], 1'b0}` 으로 LSB를 강제 0으로 만드는 이유 (ISA 규정).
- JAL은 `pc + imm`, JALR은 `rs1 + imm`. **베이스가 다릅니다.** 이게 두 명령의 유일한 본질적 차이입니다.

직접 할 일: LOAD 명령 하나의 임계경로를 손으로 따라가 보세요.
`PC → instr_mem → regfile → ALU → data_mem → 먹서 → regfile 입력`
이게 클럭 주기를 결정합니다. **싱글사이클이 느린 이유이자 파이프라인이 존재하는 이유**입니다.

### 5일차 — 메모리와 정렬

읽기: `lsu.v` → `data_mem.v`

- `wmask`가 왜 필요한지 (SB/SH 때문).
- LB vs LBU, LH vs LHU: 부호확장 대 0확장. 버그 단골입니다.
- `mem_rdata[bsh +: 8]` 가변 부분선택 문법.

직접 할 일: 테스트 프로그램의 `sb x30, 17(x23)` 한 줄을 추적하세요.
주소 0x111 → 워드 0x110의 byte1 → `wmask = 4'b0010`, `wdata = 0x5A << 8`.
파형(`make wave`)에서 실제로 그런지 확인하세요.

### 6일차 — 타이밍 가정 (가장 중요한 날)

읽기: `regfile.v`, `instr_mem.v` 주석

싱글사이클이 성립하는 조건은 단 하나입니다: **상태 소자를 제외한 모든 것이 조합**이어야 한다.

- 레지스터 읽기가 비동기여야 하는 이유.
- 명령어 메모리가 비동기 ROM이어야 하는 이유.
- **그리고 왜 이 구조가 실제 FPGA에 안 올라가는지**: Block RAM은 동기 읽기입니다. 그래서 fetch에 1사이클이 필요해지고, 그 순간 싱글사이클 가정이 깨집니다. 이게 멀티사이클/파이프라인으로 가는 실질적 동기입니다.

직접 할 일: `instr_mem.v`를 동기 읽기(`always @(posedge clk)`)로 바꿔서 시뮬레이션해 보세요. 깨집니다. **왜 깨지는지 설명할 수 있으면 이 코어는 이해한 겁니다.**

### 7일차 — 손으로 확장

더 읽지 말고, 직접 고치세요. 셋 중 하나만 하면 충분합니다.

1. 테스트 프로그램에 **반복문**을 추가하세요 (1부터 10까지 합을 메모리에 저장). 테스트벤치에 기대값 검사를 추가하고 통과시키세요.
2. `control.v`에 **illegal instruction 검출**을 추가하세요. 정의되지 않은 opcode면 `illegal` 신호를 띄우고 테스트벤치가 잡게 하세요.
3. 사이클 카운터와 명령어 카운터를 top에 추가해 **IPC를 출력**하세요. 싱글사이클이니 1이 나와야 합니다. 안 나오면 halt 처리에 버그가 있는 겁니다.

## 테스트벤치를 믿어도 되는 이유

통과하는 테스트벤치는 아무것도 안 검사하고 있을 수도 있습니다.
그래서 일부러 버그를 넣어 확인했습니다. `alu.v`의 SRA에서 `$signed()`를 빼면:

```
[FAIL] x10 = 0x7ffffffe (2147483646)   기대 0xfffffffe (-2)
❌ FAIL — 40개 중 1개 실패
```

제대로 잡습니다. 코드를 고치면서 이 테스트벤치를 회귀 검사로 쓰세요.

## 확실한 것과 확실하지 않은 것

**확실함 (실제로 실행해서 확인)**
- RV32I 정수 명령 전체가 테스트 프로그램에서 올바른 값을 냅니다 (레지스터 32개 + 메모리 8워드 검사).
- 어셈블러의 B/J 타입 인코딩은 손으로 비트를 검산했습니다.
- 테스트벤치가 실제로 오류를 검출합니다 (버그 주입 확인).

**확인하지 않음 / 범위 밖**
- FPGA 합성·타이밍 클로저는 돌려보지 않았습니다. 위에서 말한 Block RAM 문제로 이 구조는 수정 없이는 올라가지 않습니다.
- riscv-tests 같은 공식 ISA 준수 테스트는 돌리지 않았습니다. 제 테스트는 각 명령을 1~2케이스씩만 봅니다. 공식 테스트는 경계값을 훨씬 촘촘히 봅니다.
- 예외/인터럽트, CSR, FENCE의 실제 의미, 비정렬 워드 접근 트랩은 구현하지 않았습니다. RV32I 완전 구현을 주장하려면 필요한 부분입니다.
- `misa`/권한 모드 등 특권 아키텍처는 전혀 없습니다.

**이 코드에 대한 가장 강한 반박**
받아서 읽는 코드는 직접 쓴 코드만큼 안 남습니다. 특히 `imm_gen.v`의 비트 배치와 `control.v`의 진리표는, 한 번 틀려보고 디버깅해야 몸에 붙는 종류입니다.
그래서 6일차와 7일차의 "직접 할 일"이 사실 이 가이드의 본체입니다. 읽기만 하고 넘기면 일주일 뒤에 남는 게 거의 없습니다.
면접이나 랩 미팅에서 물어볼 만한 건 "RV32I 만들어봤나요"가 아니라 **"싱글사이클의 임계경로가 어디고 왜 파이프라인이 필요한가"** 입니다. 4일차와 6일차가 그 질문에 답하는 부분입니다.
